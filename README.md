# MGRS · 秘秘的 Agent 治理协议

我做秘秘，最早是想有人帮我理日程。自己的事都快理不过来了，要是再来几个 AI，各做一段，最后还得我自己记住哪个在等材料、该把谁的结果转给谁，那我只是多了几个人要协调。反过来说，要是我在主窗口交代一次，中途有变化也能直接说，哪项工作想看细一点再去工坊里看，这个助手才真正帮我省了事。[秘秘的产品哲学](docs/MIMI-OVERVIEW.md)

**MGRS（Mimi Governed Runtime Standard）是我给秘秘设计的 Agent 治理协议。** 简单来说，一个 Agent 把工作交给下一个，得把你现在要什么、可以用哪些资料、前面究竟做到了哪一步，一起交代清楚。具体怎么找资料、怎么写，留给 Agent 自己判断。

## 比如，你只说了「先给我草稿」

你有两份方案，请秘秘帮忙写个两页的比较，先看草稿。一个 Agent 可以读材料，另一个起草。写到一半，你又补了一句，「性能先放一放，我现在只关心两边怎么处理数据隐私。」

前面读过的东西还能用。把隐私条款留下，写好的性能比较先放一边。麻烦在于，你是在主窗口说的这句话，真正写稿的可能是另一个 Agent。它得收到改过的要求，知道手里哪些材料还适用。交稿时再打开看一眼，文里比较的确实是隐私条款，引用也对得上原件，这次修改才算落在了草稿上。至于发给别人，那是另外一件事，要看你接下来怎么交代。[跟着这份简报走一遍](docs/004-execution-and-evidence.md)

秘秘用 Hermes 调模型、跑工具。宿主确认当前是谁在用秘秘，Core 提供业务事实和授权记录，记忆模块从中取出这次用得上的内容。如果工作需要分开做，就到工坊去分。把这些东西接起来的是 Mimi Harness。为什么接手写稿的 Agent 得拿到你刚改的那句话，为什么回了「收到」还要看成稿，才是 MGRS 要回答的问题。这套分工也用在团队里，例如大家共用工作空间时，谁能打开哪份客户资料，仍得按各自的授权来。[架构与职责](docs/002-architecture.md)
