# MGRS · 秘秘的 Agent 治理协议

秘秘（Mimi）从个人助手做起，也面向需要协作的团队和企业。做秘秘的起点很具体：事情一多，人就得自己记住上次谈到哪儿、谁还欠一份材料、明天的安排改过几次。要是请了助手以后还得自己盯住这些细节，最费心的那部分工作其实还在人身上。[作者谈做秘秘的初衷](docs/MIMI-OVERVIEW.md#overview-1)

**MGRS（Mimi Governed Runtime Standard）规定秘秘里的 Agent 怎样接手同一件事。** 当用户改了主意、几个 Agent 各做一部分，或工具执行到一半断了线，下一步应该依据哪一版要求、谁有权做、已经做到了哪一步，都要有地方可以查。至于怎么检索、怎么写、哪些步骤适合并行，Agent 可以按任务自己选择。

## 从一句「先交草稿」开始

假设你交给秘秘两份方案，请它整理成两页比较简报，标出每个判断的出处，先交草稿。一个 Agent 可以读材料，另一个起草。写到一半，你补了一句「只比较数据隐私，性能先放一放」。

负责整理的 Agent 已经做过的工作仍然有用。两份方案的原文可以继续引用，隐私条款可以留下；按照旧要求写好的性能对比则要从这份简报里拿掉。要让起草者办到这一点，光在聊天窗口里回一句「收到」还不够。系统得把修正写回同一项任务，把修正和相应材料交到起草者手上，最后打开草稿，看结论是否真的按新要求写了。你说的是「先交草稿」，把简报发给别人还需要另一项授权。[跟着这份简报走一遍](docs/004-execution-and-evidence.md)

这件事在秘秘里由几个部分配合完成。Hermes 驱动模型调用工具、读取结果并继续工作。宿主确认是谁在使用秘秘，Core 提供相应的业务事实与授权记录。每轮请求前，记忆模块按当前任务取出相关事实；需要分工时，工坊把各自的材料和任务要求交给相应的 Agent。Mimi Harness 把这些组件接在一起。MGRS 写下它们之间要遵守的规则，让用户交代的事在换人、换窗口和中断之后仍然算数。[架构与职责](docs/002-architecture.md)

## 从哪里读起

- **想了解做这个产品时的取舍**，先读[作者的产品总览](docs/MIMI-OVERVIEW.md)。从整理自己的日程出发，作者谈到为什么让用户沿用自己的软件、决定数据放在哪里，以及隐私保护和计算成本之间的关系。接着读[设计理念](docs/000-philosophy.md)，看一份发错版本的会议纪要怎样引出治理规则。
- **想看助手怎样记住事情、接受纠正**，读[上下文与记忆](docs/003-context-and-memory.md)。关心秘秘做研究时如何找到原件、判断该信哪份材料，可以接着看[自研搜索策略](docs/006-search-strategy.md)。
- **想检查一次协作究竟有没有做好**，读[执行与交接](docs/004-execution-and-evidence.md)和[怎样验收](docs/005-review-and-conformance.md)。术语可查[核心对象](docs/001-domain-model.md)。
