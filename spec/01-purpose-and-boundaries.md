## 第一条 · 治理宗旨与个人主权边界

### 1.1 为什么个人 Agent 需要治理协议

**MGRS（Mimi Governed Runtime Standard）是秘秘面向个人持续工作与多 Agent 协作确立的治理协议。** 传统软件遵循“人点一下、程序执行一步”的确定性交互，而个人 Agent 需要在跨天例程、多轮追问、异步工具调用与多角色分工中持续代表用户行事。如果缺乏清晰的治理边界，Agent 要么因为权力过大而越界发信、误改日程，要么因为处处请示而退化为繁琐的确认弹窗机器。

MGRS 的核心目标，是把**数据主权、方法选择与行动边界**交还给个人：用户不必在“完全放手”和“步步盯防”之间二选一，而是以人类顶级秘书的协作分寸感，在明确边界内让 Agent 充分自主，在越界边缘让系统可靠止步。

### 1.2 方法自主与边界治理分离

**Agent 的自主性体现于选择方法，治理的约束体现于权限、事实、责任与效果。**

模型如何思考、采用何种推理架构、如何规划检索路径或组织工作步骤，由运行时与模型自主决定；但以下四条底线必须由可信宿主与确定性规则守住，绝不由模型的口头承诺或提示词替代：

1. **主体与版本可追溯**：每项工作都能追溯到授权主体与委托来源。受管任务的产物和操作绑定当时生效的要求版本，领域例程按业务对象、条件版本与本次运行关联回执。
2. **权能按维度委托**：用户可分别委托**有权知道（信息访问）**、**有权决定（目标之内获委托的判断与方法选择）**与**有权行动（外部副作用边界）**，并随时收窄、修订或撤回。直接指令由可信宿主确认来源。例程到点、外部事件到达或任务接续时，宿主回查相应委托的范围、期限及当前授权，再决定可以推进哪些工作。
3. **跨中断持续同一项工作**：关闭客户端窗口、压缩对话历史、切换推理模型、网络中断或宿主重启后，系统必须能找回原任务，先对账状态未知的操作，不丢失进度也不重复制造副作用。
4. **开销与风险相称**：日常对话与简单请求保持轻量直达、低开销运行；跨周期委托、多角色协作与高风险外部动作则自动启用相称的版本控制、隔离与独立核验。

### 1.3 架构立场与禁止事项

MGRS 从个人单宿主与自有轻量服务器（目标约 2 核 4 GB 体量）的真实约束出发，坚持以下工程与治理立场：

- **非 SaaS 化与生态中立**：秘秘不是绑定特定云端生态或强制代管用户数据的 SaaS 平台。Mimi Harness 复用 Hermes 的原生执行循环、会话和工具能力，通过开放接口与受控界面替用户操作既有工具，不以封闭生态锁死用户的数据与模型选择。
- **单一权威写入原则**：每项事实的权威记录都有明确归属。Core 管理用户长期事实与业务 Grant，Hermes 保存原生会话历史，Orchestration 持有受管任务合同，文件与材料依其版本化原件定位。协议禁止在既有宿主之上再造平行的“全局超级调度器”“第二套记忆写入库”或“全知管理 Agent”。
- **诚实的隐私保护分层**：自部署让用户选择数据及计算的落点，物理隔离限定硬件共享范围，网关脱敏限定转发前可见的字段，基于硬件证明链的机密计算（TEE）保护指定的计算边界。任何隐私或安全承诺都必须对应可核查的实现与验证等级，不以远期构想冒充当下默认能力。

任务准入按委托、执行环境和实际可用资源决定。开发控制面的角色、并发配置与排班只约束其自身工作。用户可选择模型、工具与算力，第三方流程插件的安装遵循当前宿主授权。[产品总览](../docs/MIMI-OVERVIEW.md) · [设计决定](../docs/DECISIONS.md)
