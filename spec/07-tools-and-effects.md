## 第七条 · 能力发现、效果分级与用户接管

### 7.1 效果分级标准（E0–E3）

一项操作的治理强度，取决于它对系统内部与外部世界造成的**实际后果（Effect）**，而不取决于模型如何描述它，也不取决于底层调用的是原生工具、MCP、外部 API、本地 CLI 还是图形界面（GUI）：

| 效果等级 | 后果性质 | 典型动作示例 | 治理与门禁要求 |
| --- | --- | --- | --- |
| **`E0` 只读观察** | 仅观察目标对象，业务状态保持原值 | 检索文献、读取日历与邮件列表、查询接口状态、网页只读浏览 | 核验当前有效读取授权（`Grant` / `scope`）与数据时效后自动放行 |
| **`E1` 有界可逆** | 影响范围有界，并有明确的撤销或回滚路径 | 保存邮件或文档草稿、写入受管中间文件、调整可撤回的个人待办 | 按当前任务与目标对象的有效写入授权执行，保留版本和可逆路径 |
| **`E2` 对外或难逆** | 跨越个人边界产生外部影响或撤销成本高昂 | 发送外部邮件/即时消息、修改共享日程、发布 Skill、提交外部表单 | 核对具体对象和发送范围。现行授权覆盖时可直接执行，非幂等操作沿同一 `request_key` 或 `effect_id` 留存回执与对账依据 |
| **`E3` 高权限与不可逆事务** | 涉及资金支付、敏感凭据、系统权限变更或不可逆重大后果 | 订单付款、转账授权、生产权限变更、不可恢复地删除核心数据、跨租户高权限操作 | 按宿主高权限策略核对显式批准，支付、不可逆的关键操作及用户保留的最终动作由本人接管。结果按目标系统回执独立核对 |

### 7.2 跨载体统一门禁与用户接管原则

1. **工具发现不等于执行授权**：无论是连接了某个 MCP Server、配置了命令行环境，还是浏览器中已登录某项服务，系统“看得到工具”或“已登录账号”均不构成自动执行所有动作的许可。每次调用前都必须按具体目标对象与动作类型核验当前授权。
2. **禁止借 CLI 或 GUI 绕过权限检查**：通过本地脚本或 GUI 模拟点击完成的操作，与直接调用 API 承受完全相同的 `E0–E3` 效果约束。
3. **关键边界交由用户亲自接管**。例如用户让秘秘预订机票，Agent 可以在授权内核对票价、行李与退改条件，填写订单，并把商户、金额和订单交给用户。资金支付、账号安全变更中须本人核验的步骤，以及不可逆的最终操作，由用户在相应服务中亲自完成。用户关掉支付页面后，秘秘仍按订单状态或付款回执判断交易结果。

### 7.3 原生执行与受管执行路由

查询日历、保存草稿、按明确授权发出一封邮件，都可以沿 Hermes 原生工具循环完成。受管分流依据工作是否需要持续管理。涉及跨会话接续、多阶段依赖、受限 Worker 分工或在途执行恢复时，Orchestration 建立任务合同，`ExecutionPort` / `ExecutorRouter` 按合同选择后端并收取相应回执。受管后端分别声明输入观察、交互、停止和恢复能力。

无论走哪条路径，执行前均核对身份、目标对象和操作权限。一次直接外发可以使用原生操作标识对账。已经进入受管任务的外发还需保留与 `task_id`、`attempt_id` 的关联。请求超时后先查原操作的实际状态。评估运行开销时，在相同负载下分别记录工具发现、冷启动连接、授权、RPC、实际处理与模型轮次，比较冷、暖路径。缓存目录与接口描述时仍须遵守 [Profile 隔离规则](10-profile-cache-isolation.md#mgrs-10)。
