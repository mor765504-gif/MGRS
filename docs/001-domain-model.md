# 001 · 换个窗口，怎么算还在做同一件事？

[首页](../README.md) · [导读目录](README.md) · [完整规范](../MGRS.md)

比如你拿到三份场地报价，让秘秘做张活动预算表。今天它把场租算好了，明天你打开另一个窗口，想补一句“把布置费也算上”。我希望你说完这句，它就能接着改。如果还得自己翻出昨天的表、再发一遍报价，把来龙去脉重新讲一遍，那换个窗口也太费劲了。

这句话对人很好懂。后台接手的 Agent 却得知道，你说的“也算上”是哪张表，昨天用的是哪三份报价，今天它还有没有权限读。MGRS 里那些看起来很细的编号，就是在这里派上用场的。

## 谁的工作，能读哪些资料

假设你在研究社团的工作配置里做这张表，个人账户里还有一份通讯录。秘秘知道两边都是你在用，读报价的助手只需要社团这边的资料。宿主先从登录会话确认你是谁（`principal`），现在用哪个账户和工作配置（`account`、`profile`），再按具体授权确定能读写的范围（`scope`）。后台助手也按自己分到的工作取得相应的资料和工具。

要是后来有一家撤回了报价的共享权限呢？宿主会检查授权有没有变过。`authorization_generation` 记录授权的代次，按老权限做的缓存也要重新检查。`native_session` 记的是实际干活的那个会话，重连或者收到后台结果时，系统靠它找回原处。[身份与授权](../MGRS.md#mgrs-2) · [工作配置与数据隔离](../MGRS.md#mgrs-10)

## 一张表为什么有好几个编号

| 回来接手时想知道什么 | 看哪条记录 |
| --- | --- |
| 还是上次那项预算吗？这次要算布置费吗？ | `task_id` 找到同一项任务，`requirement_revision` 找到当前这版要求。 |
| 上次改表时究竟保存了吗？ | `attempt_id` 找到那次执行，`receipt` 让接手者查到保存操作的结果和位置。 |
| 我眼前打开的是哪一稿？ | `result_id` 找到这份产物，以及它对应的要求版本和那次执行。 |
| 这个数是哪家报的？ | 材料引用（`MaterialRef`）指向对应版本的原报价，接手者在有权限时可以打开。数字从哪里来、怎么算出来，都属于它的来源依据（`provenance`）。 |

任务合同把要交的东西、依赖的材料和验收条件记在一起。这个例子里，要求写得简单就够了。三家得按同一个口径算，表里的每个数都能翻回原报价，那些编号才算帮上忙。[任务与交接合同](../MGRS.md#mgrs-5)

## 把布置费算上以后，旧表还能用吗？

原来算过的场租可以沿用，前提是报价还有效、接手的人还有权读取。要重算的是三家的总价，还有根据旧总价得出的排序。尤其是有一家根本没写布置费，表里得留一句“这家没写布置费”。填个零也能排出名次，看表的人却会以为这家场地免费包布置。

有时表已经存好了，只是发通知的时候断了线。这时候让秘秘重新算一遍，既浪费时间，又可能让你收到两条通知。重连后先按原来的记录打开那张表，再查刚才的通知有没有发到，从断掉的那一步接着做就好。[要求变更与效果对账](../MGRS.md#mgrs-3)

## 这轮实际交给助手什么

拿这张表来说，**上下文**里要有报价和你刚补的要求。**Persona**管秘秘平时怎样跟你商量这笔预算。**Skill**能教它把不同报价换成一个口径。真正要读文件、改表或发通知的时候，还要由宿主查它现在有权操作哪些文件、可以发给谁。

MGRS 0.1 里我希望把任务两头的事情都交代清楚，所以提出了两份合同。输入这一头叫 `ContextEnvelope`，能查出模型这轮收到了哪一版要求，用了哪些来源。交接那一头叫 `ResultCapsule`，把算好的结果、对应的报价、最后那张表和仍缺的材料留给下一位。接手的人一打开就知道还得问哪家要布置费，不用把三家的文件从第一页重新翻起。[请求级合同](../MGRS.md#mgrs-4) · [交接合同](../MGRS.md#mgrs-5)
