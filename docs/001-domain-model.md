# 001 · 核心概念：谁在做、做哪件事、凭什么算完成

[首页](../README.md) · [导读目录](README.md) · [完整规范](../MGRS.md)

假设你请秘秘根据三份场地报价编一张活动预算表。你希望今天让它读报价，明天换个窗口也能接着改。要做到这一点，接手的助手得找回三样东西：你允许它读哪些资料、你要的究竟是哪一版预算、已经算出的数字来自哪里。MGRS 用下面这些概念把它们连起来。

## 身份和数据范围

你用研究社团的工作配置打开报价，个人账户下还有一份自己的通讯录。这时，宿主根据登录会话确认操作者的身份（`principal`）、账户（`account`）和当前工作配置（`profile`），再查具体授权允许读写哪些对象（`scope`）。负责读报价的后台助手只取得这项工作所需的资料和工具。

三份报价中若有一份被撤回共享，授权代次（`authorization_generation`）让宿主识别出先前按旧权限生成的缓存。另一个标识 `native_session` 则指向实际执行这项工作的会话，供重连和接收后台结果时找到原处。[身份与授权](../MGRS.md#mgrs-2) · [工作配置与数据隔离](../MGRS.md#mgrs-10)

## 任务、尝试和结果

预算表可以改几次，过程中也可能断线。为了把两种情况分别处理，MGRS 为任务、要求、执行和产物分别保留标识。

| 接手时要问什么 | 去哪里找 |
| :--- | :--- |
| 我在接哪件事，你现在要什么？ | `task_id` 指向预算任务，`requirement_revision` 指明这一版的要求，例如是否计入布置费。 |
| 上次实际运行到了哪里？ | `attempt_id` 指向那一次执行，`receipt` 记录相应操作的效果，例如文件保存到了哪里。 |
| 眼前这张表是哪一份？ | `result_id` 将这份结果绑定到它对应的任务版本和执行尝试。 |
| 这个金额出自哪份报价？ | 材料引用（`MaterialRef`）让获授权的接手者找到对应版本的原件。数字的来源和形成依据构成它的 `provenance`。 |

任务合同记录目标、依赖、资料和验收条件。在这件事里，验收条件可以很朴素：三家的报价按同一口径列出，每个金额都找得到原件。[任务与交接合同](../MGRS.md#mgrs-5)

## 用一次资料整理看懂这些引用

第一版表格只算了场租。你补充说“把布置费也算进去”。这仍是同一项预算任务，但验收条件已经变了。下一位助手能继续使用仍获授权的三份报价，也能查阅第一版的计算过程。凡是引用过旧总价的下游比较，都要等新总价核对后再用。如果某份报价没有列出布置费，接手时应当看得见这个缺口。

再假设表格已经保存，发给你的通知却因为断线而中断。重连后，助手按原任务找到写入回执，打开对应版本的表格，再核对通知状态。这样就能从交付那一步接着做，省下重算三份报价的时间，也避免重复发送。[要求变更与效果对账](../MGRS.md#mgrs-3)

## 上下文、Persona、Skill 与权限

还是这张表。**上下文**提供本轮需要的事实，比如三份报价和你刚刚补充的布置费。**Persona**决定助手以怎样的语气和你讨论预算。**Skill**可以教它怎样对齐报价口径。到了**读取文件、写表或发送通知**这一步，具体能对哪份材料、向谁执行什么操作，由宿主按当前授权判断。

MGRS 0.1 为任务的两端提出了两份逻辑合同。输入端的 `ContextEnvelope` 供宿主回查这一轮用了哪些来源和要求。交接端的 `ResultCapsule` 把结论与支持它的材料、产物及未解决的问题放在一起。接手者因此可以直接找到“哪家仍缺布置费”，按权限打开那份报价继续核对。[请求级合同](../MGRS.md#mgrs-4) · [交接合同](../MGRS.md#mgrs-5)
