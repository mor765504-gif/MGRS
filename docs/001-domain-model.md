# 001 · 核心概念：谁在做、做哪件事、凭什么算完成

[首页](../README.md) · [导读目录](README.md) · [完整规范](../MGRS.md)

MGRS 用一组稳定引用把身份、任务、执行和证据连起来。这样，一个 Agent 退出、换模型或交接工作以后，接手者仍然能查到同一件事，而不用从一大段聊天里猜进度。

下面解释的是 0.1 设计候选中的逻辑角色，帮助阅读规范。它们不是一套已经发布的 API 定义，也不要求另建数据库。字段与权威归属见[规范第 2 章](../MGRS.md#mgrs-2)。

## 身份和数据范围

| 概念 | 回答的问题 | 使用时要保留的区别 |
| :--- | :--- | :--- |
| `principal` | 这次操作基于谁的可信身份？ | 身份来自宿主真实会话，模型自称某种角色不能建立身份 |
| `account` | 这份身份、数据和授权关联哪个账户？ | 账户信息要与 Profile、会话和授权范围一起核对 |
| `profile` | 当前使用哪组会话、记忆、Persona、Skill 和工具配置？ | Profile 名称不是权限证明；共享数据仍需有效授权 |
| `scope` | 哪个数据或对象范围允许当前主体读取或修改？ | 已撤回、已过期的内容不能靠缓存继续使用 |
| `native_session` | 这项工作对应哪个原生执行会话？ | 新开界面或重连后仍需找回正确会话，避免把结果送给别的任务 |
| `authorization_generation` | 当前引用的授权属于哪个有效代次？ | 旧代次不能覆盖撤权后的现实状态 |

例如，研究 Profile 可以使用某份已授权资料；它不会因为名字叫“研究助手”，就获得所有项目的资料。后台 Worker 的权限还要按具体任务授予。详细边界见[不变量 G01、G02、G07](../MGRS.md#mgrs-3)和[Profile 隔离](../MGRS.md#mgrs-10)。

## 任务、尝试和结果

| 概念 | 含义 | 为什么单独保留 |
| :--- | :--- | :--- |
| `task` / `task_id` | 一项有目标、输入、结果条件和依赖的工作 | 一件事可以跨多个会话与尝试继续进行 |
| `requirement_revision` | 当前任务要求的版本 | 任务要求变化要有新版本；旧结果不满足新版本要求，相关下游依据失效并等待确认 |
| `attempt_id` | 某次实际执行的标识 | 恢复时需要核对哪次执行发生了什么，不能只看任务标题 |
| `result_id` | 一份具体结果的标识 | 结果要绑定任务版本和尝试，才能判断是否仍然有效 |
| `receipt` | 执行、业务操作或交付产生的可追溯回执 | “我完成了”的文本不能替代实际效果记录 |
| `MaterialRef` / 材料引用 | 指向原件或产物的稳定、可核对引用 | 接收者可按权限读取必要证据，不必复制全部上游聊天 |
| `provenance` | 来源及其追溯信息 | 让结论能回到相应版本、材料和实际观察 |

这里的“合同”指把目标、适用范围、依赖与结果条件明确记录下来，供运行时与接收者核对。它不意味着每个小请求都要增加一轮填写表单的步骤，见[任务合同](../MGRS.md#mgrs-5)和[任务纪律](../MGRS.md#mgrs-6)。

## 用一次资料整理看懂这些引用

假设用户要求整理三份已授权材料并写出综述。任务 `T` 的要求版本是 `1`，Worker 在尝试 `A1` 中生成结果 `R1`。结果附上所用材料的版本引用，接收者据此核对结论。

随后用户补充“只讨论某个时间段，并保留资料之间的分歧”。这是任务要求的变化，应形成新版本。即使 `R1` 写得流畅，它仍属于版本 `1`；后继工作不能悄悄把它当成新版本已经验收的成果。

如果结果已经保存，但通知发送中断，恢复时要分别检查结果和通知的回执。不能因为用户没有收到通知，就认定研究未执行；也不能因为 Worker 结束，就声称用户已收到成果。任务要求变化由 [G05](../MGRS.md#mgrs-3) 约束；执行完成、通知送达与外部交付则按 [G03](../MGRS.md#mgrs-3) 和[结果交接层级](../MGRS.md#mgrs-5)分别核对。

## 上下文、Persona、Skill 与权限

这四者经常一起进入一次任务，却各自回答不同的问题。

| 概念 | 负责说明 | 不能据此推导 |
| :--- | :--- | :--- |
| 上下文 | 本轮需要哪些有效事实、任务要求和材料 | 某条信息出现在 Prompt 中就具有授权效力 |
| Persona | 持续身份设定、声音、语气与场景表达 | 角色描述能够扩大数据或工具权限 |
| Skill | 做某类工作的适用方法、依赖与输出约定 | 读取 `SKILL.md` 就获得脚本、MCP 或外发权限 |
| 宿主授权 | 当前主体可对哪些对象执行哪些操作 | 工具已安装、可发现或模型想调用就必然获准 |

`ContextEnvelope` 用来记录本轮上下文的身份、来源、选择和预算；`ResultCapsule` 用来组织交接的结论、证据、产物与未解决问题。二者在规范中都是拟议的逻辑合同。生成一段符合示例结构的 JSON，本身不能证明内容已被消费或通过验收。参见[第 4 章](../MGRS.md#mgrs-4)、[第 5 章](../MGRS.md#mgrs-5)及[冲突裁决](../MGRS.md#mgrs-15)。
