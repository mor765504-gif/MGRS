## 3. 长对话 2×2 参数对照（真实模型 + 合成任务）

实验 D 让真实模型在 Hermes 压缩器和 `mimi_tavern` 上跑长对话，工具动作由测试程序模拟。推理强度选 `high` 和 `max`，压缩门槛选 `128K` 和 `160K`，两两组合。每种组合各跑一次，原计划每次聊 46 轮。

| 指标 | high / 128K | high / 160K | max / 128K | max / 160K |
| :--- | ---: | ---: | ---: | ---: |
| 实际完成轮数 | 46 | 46 | 37（预算停） | 6（手动停） |
| 已考事实题 | 7/7 | 7/7 | 4/4（部分） | 未进行 |
| 压缩次数及位置 | 1 次，第 33 轮 | 1 次，第 44 轮 | 3 次，第 9/16/26 轮 | 0 次 |
| 原报告缓存命中率 | 71.8% | 84.9% | 67.4% | 48.6% |
| 响应 P50/P90 | 2.5 / 3.8 秒 | 2.5 / 4.0 秒 | 8.2 / 49 秒 | 60 / 118 秒 |
| 每次调用推理 token | 138 | 139 | 3208 | 11560 |
| 该格花费 | ¥1.62 | ¥1.19 | ¥3.03 | ¥1.29 |
| 未被要求的写日历 | 2 | 2 | 4 | 0 |

同样用 `high`，这一次把门槛设在 160K 的那组少花了约 26.5%（原报告取整为约 27%），缓存命中率高 13.1 个百分点，七道事实题两组都答对了。要弄清这 13.1 个百分点里有多少来自门槛，还得看每轮请求的缓存在哪里断开，并用同样的任务再跑几次。

有两个细节会影响怎么读这张表。`high/160K` 到第 44 轮才压缩，留给它回答压缩后问题的机会很少。两组 `high` 还各有 2 次想在没人要求的情况下写日历。`max` 的两组都中途停了，表里的答题数和费用只算到停止那一轮。

## 4. 推理强度、记忆密度与其他对照

- **C：推理强度探测。** 同题四档各 2 次，无工具；报告观察到 `max` 的推理用量明显较大，但 `low/medium/high` 难以区分。样本不足以给出普适推理强度排名。
- **E：medium/high 对照。** 13 个用例 × 2 样本，每档累计 74 轮。`medium` 的每次调用推理 token 均值/中位数为 206/136、每轮响应 P50/P90 为 2.9/6.4 秒、输出合计 31,794 token；`high` 对应为 244/162、3.0/6.3 秒、34,560 token。报告按该批受控样本逐条复看，真实虚假断言/越权计数均为 0；不能由此推导所有任务均无幻觉或越权，也不能用 E 覆盖 D 的异常记录。
- **F：实际 token 密度。** 事实记忆 2171 字符对应 1099 token；用户记忆 1337 字符对应 795 token。系统提示词 14,129 字符对应 4,368 token，7 个工具定义对应 5,155 token，固定部分约 9,500 token，`mimi_tavern` 约再增加 1,000 token。原生记忆额度扩到 10000/6000 且**假设写满**时，报告估计记忆约 8,500 token、固定部分约 1.7 万 token，占 160K 门槛约 11%；这后一项是依据测得密度作的容量估算，不是已写满状态的实测。
- **研究依据。** 报告明确参考 Hermes 官方文档、DeepSeek 论文中 MRCR 长上下文指标及社区故障/经验，再与上述实测组合决策；其所引 V4-Flash MRCR 数字为 128K 0.87、256K 0.76。**本次未独立重新读取对应论文和社区帖原文，故这些数字标为历史报告引用，而非本次新验证的外部事实。**

## 5. 9 月 26 日采用的配置

| 2026-09-26 当时配置 | 主要决策依据 | 历史状态 |
| :--- | :--- | :--- |
| `agent.reasoning_effort: high` | C/D/E 中 `max` 成本及延迟明显上升，未测得相称准确率收益 | 报告称已部署至旧 `default/maint` |
| `compression.threshold_tokens: 160000` | D 中两组 `high` 均通过已测事实题，160K 样本花费低；参考 B 的线上长度及报告转述的 MRCR | 同上；仍非普适最优值 |
| `memory.memory_char_limit: 10000` / `user_char_limit: 6000` | B 的旧记忆饱和与拒写、F 的 token 密度/固定成本估算、社区经验 | 同上；这是**Hermes 原生记忆容量** |
| 不开启 `proactive_prune_tokens` | 报告评估了历史改写与缓存前缀受扰风险 | 当时决策；不代表新候选当前配置已经读回 |

历史报告还记录了原先曾先后建议不同记忆额度、考虑启用提前裁剪、提出修改 `protect_last_n`，后来依据测试或源码撤回的过程。

## 6. 这些参数分别作用在哪里

| 参数 | 影响的环节 |
| --- | --- |
| 160000 token | 旧 Hermes 会话达到这一长度时触发压缩。 |
| 10000 / 6000 字符 | 9 月调整后的原生 MEMORY / USER 存储额度。 |
| 2000 字符 | 后续 `mimi_memory` 从 Core 快照选取事实，每轮自动放入模型请求的文本预算，包含元信息。 |

11 月这版代码会跨 scope 找字词、中文双字和路径的匹配，再结合 importance 选出这一轮带给模型的事实，记下哪些没放进去。想知道把 2000 字符调大或调小会怎样，得另做对照，看模型找回了哪些相关事实、缓存花了多少钱、任务最后做得怎样。9 月实验改的是会话压缩门槛，两种设定回答的问题不同。[MGRS 第 16 章](../reference/mgrs-0.1-technical.md#mgrs-16)
