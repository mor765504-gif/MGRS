# 000 · 我为什么给秘秘做一套治理协议

[首页](../README.md) · [产品哲学](MIMI-OVERVIEW.md) · [协议全文](../MGRS.md)

比如你跟秘秘说，会议纪要改好以后，明天发给参会的人。一个 Agent 把定稿存好了，另一个也按时发了邮件。第二天大家点开附件，怎么还是昨晚那一版？

你去看文件夹，新稿确实在。去看发件箱，邮件也确实发了。可你交代的事还是没办好。之前有朋友问我，几个 Agent 都会互相交流了，那协作能力的高低怎么看？我比较在意的就是这种地方。写纪要的那个把哪份稿交了出去，发邮件的那个最后又拿了哪一份，中间得对得上。这也是我为什么专门给秘秘做一套治理协议。[当时关于多 Agent 的讨论](sources/2026-11-09-bilibili-bv1vix26sEzR.md)

## 有些事我愿意让 Agent 自己选

改纪要是先读一遍草稿，还是先翻会议材料核对有争议的那句话？都可以。材料少，秘秘自己改就好了。附件多，也可以让另一个有权读附件的 Agent 帮忙核出处。要是连这种先后顺序都规定死了，碰到稍微不一样的任务，反而还要绕一圈。[任务纪律](../MGRS.md#mgrs-6)

但你中途说了一句「名单有误，只发给这四个人」，这句话就得一路传到真正发邮件的那个 Agent。假如你在主窗口看到秘秘回了「好」，后台却还拿着昨天的名单，你会很自然地以为它已经改了。按 MGRS 的设计，这句补充要记到原任务上，发送时按新版名单核对收件人和附件。就算旧稿晚一步才送到，也能认出它是按哪一版要求写的。[任务怎样交接](../MGRS.md#mgrs-5)

## 秘秘很熟悉你，帮它查附件的 Agent 需要知道多少？

我希望跟秘秘聊久了，它能记住我的习惯。比如我喜欢纪要把待办单独列出来，下次还得从头解释，就谈不上有多懂我。但我这次说「只发给这四个人」，总不能让它以后每次开会都默认是这四个人。

所以我会把这两句话分开放。写纪要的习惯可以记成长期偏好，收件人跟着这一场会议走。今天我纠正名单，就改这项任务。以后我改了写作习惯，就更新那条偏好。至于后台负责核附件的 Agent，把那几页给它看就够了。主会话和我聊过的其他私事，它用不上，也没有理由跟着这份纪要传过去。MGRS 里讲的记忆、任务和授权，落到人身上就是这么个区别。[上下文与记忆](003-context-and-memory.md)

## 断网以后，要不要再发一次？

假设点击发送以后，服务端还没把结果传回来，网络就断了。这个时候再点一下重试很容易。可第一封到底发出去没有？秘秘得先去查，不然那四个人可能各收到两封。我的想法是，让秘秘记得刚才发的是哪一次，重连以后拿原来的发送记录去查。有已发送的回执，就告诉你发了。查清楚没发，再按原来的授权继续。要是那边暂时也查不出来，就告诉你纪要已经改好，发送还在等确认。你至少知道可以接着处理哪一步。[执行与恢复](004-execution-and-evidence.md)

换个简单点的问题，你早上只想知道今天几点有会，我希望秘秘看一眼日历就回答。为了查个时间还得让你确认一遍计划，再等两个 Agent 商量，那我做这个助手图什么呢？发会议纪要倒值得多花一点工夫，毕竟附件和收件人一旦选错，麻烦会落到别人身上。[工具与效果等级](../MGRS.md#mgrs-7)

真要比较两种做法，我会拿同一批纪要来看。先看有多少份按时发对了人，再把中途改名单、断网的那几次也算进来。连返工一起，到底花了多少钱、让人等了多久？如果后台那一轮确实变快了，我还想知道用秘秘的人有没有因此少操一点心。[怎样判断协作是否可靠](005-review-and-conformance.md)
