# 000 · 设计理念

[首页](../README.md) · [导读目录](README.md) · [完整规范](../MGRS.md)

MGRS 希望让 Agent 在已有授权内持续把事做完，并让用户能看清它实际做到了哪一步。这要求系统在多次对话、多个 Worker、多个工具和一次次恢复之间，始终保留目标、权限、来源与结果的联系。

本篇解释 [MGRS 0.1 第 1 至 3 章](../MGRS.md#mgrs-1)的设计方向。它属于导读，不新增治理条款，也不把设计候选描述成已完成的产品能力。

## 从组件之间的问题出发

设想一个 Worker 已完成资料整理，但它的结果停在自己的会话里。主控看到“成功”状态后继续写结论，真正使用的仍是旧材料。再设想用户更改了目标，新要求虽然进了 Inbox，下一轮请求却没有带上它。两种情况下，局部状态都可能成立，整个任务依然偏离要求。

MGRS 因而关注交界处：一个状态是谁写的，对应哪个版本，交给了谁，接收者有没有实际消费，最终产物通过了什么检查。任务可靠性要沿这条链判断。相关区别在 [G03、G05 与 G06](../MGRS.md#mgrs-3)中写明。

## 每项事实都有负责的地方

Core 中的事实、原生会话里的执行记录、任务系统中的要求版本，各有自己的权威来源。抽屉视图、上下文摘要和前端进度页，从这些来源整理读者或模型需要看到的内容。

这样做的实际收益是：当两处显示不一致时，能够回到负责该事实的地方核对。用户撤回了资料，就按当前授权和撤回状态处理；一个旧摘要仍提到它，并不能让它重新有效。修改 `memory.md` 的展示内容，也不能静默覆盖 Core 中的事实。

“唯一权威”落实到每一类事实的写入职责。组件可以有各自的物理存储，关系与边界见[规范第 2 章](../MGRS.md#mgrs-2)和[第 4 章](../MGRS.md#mgrs-4)。

## 上下文按任务装配

长期相处需要记忆，复杂工作需要材料，但每一轮真正需要的信息并不相同。人物设定、稳定事实、当前任务修正、方法说明和历史原件，各有自己的来源和装配规则。

抽屉的作用是提供当前可读、相关、带来源的视图。必需约束优先保留，可选事实按明确规则选择，未选内容保留可回查路径。用户的任务修正不能因为普通记忆预算不足而悄悄消失。预算、遗漏与压缩规则见[规范第 4 章](../MGRS.md#mgrs-4)。

## 治理成本随任务而定

用户明确交代的小任务，应在有效授权内直接推进。复杂依赖需要可检查的任务合同；涉及外部发送、共享对象或难以逆转的操作，需要相应授权和效果对账。已有授权是否涵盖当前动作，应由真实范围判断。

这也意味着需要克制流程本身：不用为了凑齐角色而增加 Worker，不要求每次输出都经过另一个模型，不让已经确定的任务反复进入规划或确认。MGRS 的目标同时包含可靠性和低开销，具体规则见 [G12](../MGRS.md#mgrs-3)、[任务纪律](../MGRS.md#mgrs-6)与[工具效果等级](../MGRS.md#mgrs-7)。

## “完成”需要说明完成了什么

产物生成、结果保存、接收方收到、产物通过检查和外部发布成功，是可以分别成立的事实。协议要求这些状态各有依据，避免一句“已完成”把中间缺口抹掉。

遇到工具超时或进程中断时，也保留这个原则：外部效果未知就先对账原尝试。给操作换一个编号重试，可能把已经成功的发送再做一遍。恢复过程要接续原任务和回执，具体见[规范第 5 章](../MGRS.md#mgrs-5)与[第 11 章](../MGRS.md#mgrs-11)。

## 用整项任务衡量改进

节省了某轮 token，可能又因为漏掉关键事实而多跑几次；更快的工具发现，也不能抵消越权调用。因此，评价改造需要同时看任务质量、交接与恢复可靠性、延迟和总用量，并说明版本、样本和失败情况。

当前规范已经列出要观察的指标与负面场景，尚未凭空规定统一性能数字。源码存在、受控检查通过、真实模型运行和生产实测分别说明不同范围的事实，完整口径见[规范第 13 章](../MGRS.md#mgrs-13)。
