# 000 · 为什么要治理 Agent 之间的协作

[首页](../README.md) · [产品哲学](MIMI-OVERVIEW.md) · [协议全文](../MGRS.md)

设想你交代了一件小事：“把会议纪要改好，明天发给参会的人。”负责修改的 Agent 留下一份定稿，负责发送的 Agent 手里却还有昨晚的版本。各自的工作都可能显示成功，参会者收到的依然是一份旧纪要。让两个模型分别更擅长写作和发邮件，解决不了交接时用错版本的问题。

在讨论多 Agent 时，秘秘作者把自己的关注点概括为从“怎么让多agent有效协作”转向“如何治理协作”。MGRS 从那些容易掉在两个人或两个组件之间的事情入手。谁接到了哪一版要求？接手的人拿到了什么？如果工作突然中断，回来后从哪里继续？[作者答疑](sources/2026-11-09-bilibili-bv1vix26sEzR.md)

## 方法交给 Agent，结果有地方核对

修改纪要的人可以先读草稿，也可以先找会议材料里有争议的一段。材料不多时，一个 Agent 就能完成。材料很多时，协调者也可以把查出处的工作交给另一个有权读取资料的 Agent。用户真正关心的是，最后保留了哪些决定，待办分给谁，收件人收到的是哪一版。MGRS 把约束放在这些人与人、组件与组件需要彼此信赖的地方。模型仍然可以按问题选择工作方法。[任务纪律](../MGRS.md#mgrs-6)

假如你补充“参会名单有误，只发给这四个人”，这项修改就要跟着任务进入接下来负责发送的请求。工坊显示“已收到补充”只能回答第一件事。用户要知道修改产生了作用，可以查看实际准备发送的对象和纪要版本。一旦旧版本到得更晚，记录中的任务版本让宿主认得出它属于哪一次工作。[任务交接](../MGRS.md#mgrs-5)

## 熟悉用户，只取眼前用得上的记忆

长期相处的好处，是昨天说过的事今天还能接着做。但修改会议纪要的人，只需要这场会的资料、当前要求，以及与写作有关的少数偏好。后台 Worker 是否能读一份私下讨论，要看用户授予这项任务的范围。人和助手逐渐熟悉，跟一个同事能打开哪些文件，是两种不同的关系。

用户纠正了参会名单，就去更新这项任务；撤回了一条长期偏好，就去更新保存那条偏好的记录。下次需要时，从相应来源取当前有效的内容。这样，留在旧草稿、摘要或界面里的名字都有出处可查，也有判断它今天是否还适用的办法。这就是 MGRS 说的“每项事实有自己的权威来源”。[上下文与记忆](003-context-and-memory.md)

## 中途停下来，也能把同一件事接下去

邮件发出时断网，界面上的等待提示消失了。此时再点一次，可能让四个人各收到两封邮件。MGRS 要求宿主保留这次发送的标识，重连后先查原服务的回执。查到已发送，就接着报告结果；查清尚未发送，才按原授权继续；服务还无法判定，就把这次发送留在待核对状态。重新打开窗口、换模型接手，都可以沿着同一个操作查下去。[执行与证据](004-execution-and-evidence.md)

仅仅问“明天有哪些会”，助手可以在已有授权里查日程、直接回答。要修改共享纪要并寄给他人，版本、收件人和外部发送回执才逐一成为必要条件。给简单查询硬加规划和复核，要花用户的时间。把同样的步骤从外发中省掉，代价则可能落到收到旧稿的同事身上。治理的分量由实际动作及其后果决定。[效果等级](../MGRS.md#mgrs-7)

用这个例子评价一次改进，可以看同样一批任务里有多少人按时收到了正确的纪要，中途改要求或断网的那些次是否也办成了，以及完整做完共用了多少时间和模型费用。把返工和恢复也算进来，才知道省下的时间究竟落在模型的一次回复上，还是落在了用户办完这件事的过程里。[审查与符合性](005-review-and-conformance.md)
