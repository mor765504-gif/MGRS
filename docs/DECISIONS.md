## D01 · 协议而非独立运行中间层

**状态：用户明确确认。**

用户原话：“肯定是协议啊 我就得拿来好好的和大家聊一下我这套治理协议到底情况是怎么样的”。

归档含义：MGRS 是约束秘秘组件协作的协议，不新增一个独立 Agent 框架或调度中间层。协议正文、秘秘实现与验证材料可以分别讨论。

## D02 · 秘秘内部专有标准，允许外部讨论与审查

**状态：对话已选定的定位。**

用户选择“主要用于秘秘内部，但允许其他开发者参与讨论和审查的专有标准”；随后对话沿此定位继续。

归档含义：首先服务秘秘，不因外部可讨论而自动变成行业通用协议或开源软件。可公开的规范段落、许可条款及邀请名单仍应另行确定。仓库本身现已公开为 `mor765504-gif/MGRS`。

2026-11-12 表述澄清：本条「专有」指秘秘自有、自主设计的标准，区别于采用外部厂商方案，不指封闭许可。此前「许可条款仍应另行确定」已由 D16 完成；「不因公开而自动变成行业通用协议」仍成立——公开文本授权不等于放弃框架的解释权与演进方向。

## D03 · 治理合同自洽，不引入外部工作流框架依赖

**状态：用户明确要求。**

归档含义：MGRS 与秘秘实现自己定义控制权和任务纪律；不把第三方通用工作流/技能框架当作治理依赖。保留已有 Core、Hermes 和工坊成果。对外文档不点名具体第三方框架。

## D04 · C0 判断与验收事实的边界

**状态：此前对话按认可处理；完整授权边界尚未逐条定稿。**

此前讨论提出：C0 保留规划、协调、判断和修复建议权，但不凭判断改写真实回执或绕过已经确定的验收条件。用户回复“对的”，助手据此沿这一方向继续。

这份认可不能扩展为 C0 已被授权任意修改验收规则、删除失败记录或降低交付目标。对应条文见[技术参考](reference/mgrs-0.1-technical.md)第 5、6、15 章。

## D07 · 多 Agent：从「如何协作」转向「如何治理协作」

**状态：公开技术讨论中确认的设计焦点（2026-11-08）。**

来源：B 站技术答疑自述（[BV1vix26sEzR](https://www.bilibili.com/video/BV1vix26sEzR/)）。

归档含义：多 Agent 能力本质是 harness 调度与工程治理。工程长尾与假验收需要专门合同与证据分层；协作高低用准确率、延迟、用量/成本、任务可靠性衡量。MGRS 只讨论这些治理机制，不比较外部产品功能清单。

## D08 · Hermes 为运行底座；抽屉 / Persona / 工坊补治理合同

**状态：公开技术讨论中确认（2026-11-07）。**

归档含义：复用 Hermes 的 MCP、Skill、心跳与 Agent Loop；其上下文管理偏保守处，由只读抽屉投影、Persona 装配与工坊任务隔离补强。单入口与工坊可共享基本记忆视图，但不全部继承上下文。禁止另建第二套可写记忆账本或第二个 Agent Loop。

## D09 · 信息源质量属于方法层治理输入

**状态：公开技术讨论中确认（2026-11-07）。**

2026-11-09 补充确认：上述讨论指秘秘自研搜索策略。具体归属和实现入口见 D14 及[搜索策略导读](006-search-strategy.md)。

## D10 · 隐私与部署：零访问加密计算为技术路径；单宿主 / 自有 VPS 为假设

**状态：公开技术讨论中确认（2026-11-07〜08）。**

归档含义：目标方向包括算力侧零访问（TEE / 机密计算一类路径）与可选隐私网关脱敏；物理隔绝与密码学是不同技术路线。鼓励自有 VPS / 低功耗单宿主 24h 运行；约 2C4G 为架构体量目标而非已测容量。协议可强制的是授权、隔离、撤回与证据；加密推理是否达标仍为待证实施。

## D15 · 治理可观察行为与效果，保留方法自主性

**状态：用户确认的总览核心表述（2026-11-09）。**

归档含义：MGRS 约束权限、版本、交接、实际效果、验收与恢复，不强制规定模型内部的思考过程、规划顺序或模型架构。“Agent 的自主性体现于选择方法；治理的约束体现于权限、事实、责任和效果。”基础不变量持续生效，复杂协作与复核按任务需要启用，不把固定多轮规划或常驻 Reviewer 变成所有请求的必经步骤。

本条说明治理对象和自主性边界，具体 C0 调整验收方式的权力仍需按 D04 / D05 与开放问题逐项界定，未据此扩张为任意修改验收目标的权限。
