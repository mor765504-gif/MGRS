## D01 · 协议而非独立运行中间层

**状态：用户明确确认。**

用户原话：“肯定是协议啊 我就得拿来好好的和大家聊一下我这套治理协议到底情况是怎么样的”。

归档含义：MGRS 是约束秘秘组件协作的协议，不新增一个独立 Agent 框架或调度中间层。协议正文、秘秘实现与验证材料可以分别讨论。

## D02 · 秘秘内部专有标准，允许外部讨论与审查

**状态：对话已选定的定位。**

用户选择“主要用于秘秘内部，但允许其他开发者参与讨论和审查的专有标准”；随后对话沿此定位继续。

归档含义：首先服务秘秘，不因外部可讨论而自动变成行业通用协议或开源软件。可公开的规范段落、许可条款及邀请名单仍应另行确定。仓库本身现已公开为 `mor765504-gif/MGRS`。

## D03 · 治理合同自洽，不引入外部工作流框架依赖

**状态：用户明确要求。**

归档含义：MGRS 与秘秘实现自己定义控制权和任务纪律；不把第三方通用工作流/技能框架当作治理依赖。保留已有 Core、Hermes 和工坊成果。对外文档不点名具体第三方框架。

## D07 · 多 Agent：从「如何协作」转向「如何治理协作」

**状态：公开技术讨论中确认的设计焦点（2026-11-08）。**

来源：B 站技术答疑自述（[BV1vix26sEzR](https://www.bilibili.com/video/BV1vix26sEzR/)）。

归档含义：多 Agent 能力本质是 harness 调度与工程治理。工程长尾与假验收需要专门合同与证据分层；协作高低用准确率、延迟、用量/成本、任务可靠性衡量。MGRS 只讨论这些治理机制，不比较外部产品功能清单。
